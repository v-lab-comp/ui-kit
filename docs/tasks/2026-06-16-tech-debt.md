## 🧹 Задача 1 — Унификация маркера обязательного поля (`required`)

### Текущая ситуация

Звёздочка `*` обязательного поля рисовалась по-разному в разных компонентах: в инпутах цвет был зашит на `--primary-base` (синий), в `FileUpload` — тоже синий, без единого источника. Цвет/отступ/размер не выносились наружу, переопределить тему было нельзя. Дизайн требует красный маркер.

### Целевое состояние

Единый маркер обязательного поля во всех компонентах с label: цвет из CSS-переменной `--input-required-color` (дефолт `--error-base`, красный), проп `requiredMarker?: ReactNode` для замены символа. `InputField`, все текстовые поля, `DateInput`, `PhoneInput`, `SelectInput`, `AsyncSearchSelect`, `TagInput` и `FileUpload` используют один и тот же подход.

### Trade-offs

- **Выигрываем:** единый источник стиля маркера, темизация одной переменной, консистентный UX, меньше дублирования CSS.
- **Риски:** смена цвета синий → красный — визуальный breaking change для тех, кто привык к синему; нужно проверить, что нигде не было локальных переопределений на синий.

### Сценарий миграции

- Шаг 1: ввести переменную `--input-required-color` и проп `requiredMarker` в `InputField`.
- Шаг 2: пробросить `requiredMarker` через все поля-обёртки.
- Шаг 3: перевести `FileUpload` (`.dropZoneRequired`) с `--primary-base` на `--input-required-color, var(--error-base)`.
- Шаг 4: обновить сторис и доки.
- Откат: `git revert` коммитов с маркером; либо переопределить `--input-required-color: var(--primary-base)` в теме.

### Метрики успеха

- Во всех компонентах с `required` маркер одного цвета (визуальная проверка сторис/Storybook).
- Смена цвета маркера темы делается одной CSS-переменной без правок компонентов.
- Нет хардкода `--primary-base` для маркера в кодовой базе (grep пуст).

## 🧹 Задача 2 — Иерархия состояний рамки полей ввода

### Текущая ситуация

Рамка инпута не отличала пустое поле от заполненного. Фокус-рамка и кольцо были на нейтральных токенах (`--stroke-strong-950` / `--neutral-alpha-16`), не на бренд-цвете. Пользователю было неочевидно, в каком поле уже есть значение и какое сейчас в фокусе.

### Целевое состояние

Чёткая иерархия состояний: пусто (серый) → есть значение `--blue-400` → фокус `--primary-base` + primary-кольцо → ошибка (красный). Заполненность текстовых полей определяется автоматически (`BaseInput` выставляет `data-filled`); для контролов без `<input>` (Select и др.) — проп `filled?: boolean`. Работает для всех текстовых полей, `DateInput`, `PhoneInput`, `SelectInput` (full + compact), `AsyncSearchSelect`, `TagInput`.

### Trade-offs

- **Выигрываем:** яснее визуальный статус формы, единая логика заполненности, бренд-цвет в фокусе.
- **Риски:** новый атрибут `data-filled` и токен `--base-input-border-filled` — нужно следить, чтобы все обёртки прокидывали `filled`; возможны расхождения там, где значение задаётся нестандартно.

### Сценарий миграции

- Шаг 1: добавить `data-filled` в `BaseInput` и токен `--base-input-border-filled`.
- Шаг 2: добавить проп `filled` в `InputField` + правило filled-рамки.
- Шаг 3: пробросить `filled` / `data-filled` в `SelectInput` (full + compact) и остальные поля.
- Шаг 4: перевести фокус-токены на `--primary-base` / `--primary-alpha-16`.
- Откат: `git revert`; либо вернуть прежние значения токенов рамки/фокуса.

### Метрики успеха

- Все перечисленные поля визуально проходят 4 состояния в Storybook.
- Заполненное поле отличимо от пустого без фокуса (ручная проверка).
- Нет полей, где `filled` не отрабатывает (чек-лист по списку компонентов).

## 🧹 Задача 3 — Синхронизация палитры примитивов с дизайн-токеном

### Текущая ситуация

Часть примитивов в `primitives.css` расходилась со значениями из дизайн-токена (`slate-200`, `blue-400`, `green-100`, `purple-500`, `pink-400`, `neutral-500`). Это давало визуальные расхождения между макетом и реализацией.

### Целевое состояние

Примитивы соответствуют дизайн-токену: `slate-200` `#eaecf0`, `blue-400` `#4c82ff`, `green-100` `#d6f5e8`, `purple-500` `#7d52f4`, `pink-400` `#ff68b3`, `neutral-500` `#7a7a7a`. `primitives.ts` сгенерирован из `primitives.css` через `npm run gen:primitives` (не правится вручную).

### Trade-offs

- **Выигрываем:** соответствие макету, единый источник правды (CSS → генерация TS).
- **Риски:** изменение базовых цветов влияет на все компоненты, которые их используют, — возможны неожиданные сдвиги оттенков в местах, где примитив использовался напрямую.

### Сценарий миграции

- Шаг 1: обновить значения в `src/skins/corporate/primitives.css`.
- Шаг 2: перегенерировать `src/colors/primitives.ts` (`npm run gen:primitives`).
- Шаг 3: визуально проверить компоненты, завязанные на изменённые примитивы.
- Откат: `git revert` коммита с палитрой + регенерация.

### Метрики успеха

- Значения примитивов совпадают с дизайн-токеном 1:1.
- `primitives.ts` соответствует `primitives.css` (генерация без диффа).
- Нет визуальных регрессий на ключевых компонентах (ревью сторис).

## 🧹 Задача 4 — Мультиязычность и валидация `FileUpload`

### Текущая ситуация

Все видимые строки `FileUpload` были захардкожены на русском («Выберите файл…», «Загрузить файл», статусы «Загрузка…/Готово/Ошибка», подписи кнопок). Использовать компонент в мультиязычном продукте было нельзя без форка. Лимит размера файла и допустимые типы не контролировались как входящие пропсы.

### Целевое состояние

Все тексты вынесены наружу через проп `texts?: FileUploadTexts` (дефолты в `DEFAULT_FILE_UPLOAD_TEXTS`, RU): `title`, `subtitle`, `button`, `uploading`, `done`, `error`, `download`, `remove`, `ofLabel`. Лимит — проп `maxSize?: number` (байты): файл сверх лимита помечается статусом `error`. Допустимые типы — проп `accept`. Компонент готов к i18n без изменения исходников.

### Trade-offs

- **Выигрываем:** компонент пригоден для любых языков, контроль размера/типов на стороне потребителя, нет форков ради перевода.
- **Риски:** расширение API (новые пропсы) — нужно поддерживать актуальность набора ключей `FileUploadTexts`; валидация `maxSize` сейчас только помечает статус `error`, без отдельного коллбэка/сообщения об ошибке (возможна будущая доработка).

### Сценарий миграции

- Шаг 1: ввести `FileUploadTexts` + `DEFAULT_FILE_UPLOAD_TEXTS`, пробросить `texts` в `FileUploadField` / `FileDropZone` / `FileUploadItem`.
- Шаг 2: добавить `maxSize` + валидацию размера в `handleFiles`.
- Шаг 3: задокументировать `accept` как входящий проп.
- Шаг 4: стори `i18n + maxSize`, доки RU/EN/UZ, changelog.
- Откат: `git revert` коммита `feat(fileupload): i18n texts, maxSize, red required marker`.

### Метрики успеха

- Все видимые строки компонента переопределяются через `texts` (проверка на узбекской локали в Storybook).
- Файл > `maxSize` визуально получает статус `error`.
- В исходниках компонента не осталось захардкоженных пользовательских строк (grep пуст).
