# Модификаторы частей компонентов не описаны в контрактах

**Статус:** открыто · **Приоритет:** средний — до второго скина · **Заведено:** 2026-11-10

## Текущая ситуация

Контракт (`src/theme/contracts/<name>.ts`) описывает корень: `attributes` и `states` рендерятся на корне компонента, `parts` — список внутренних элементов. Но около 28 data-атрибутов стоят на **частях** и в контрактах не описаны: `data-highlighted` и `data-multi` у опции `SelectInput`, `data-exiting` / `data-mounted` у тоста, `data-side` / `data-status` у `Drawer`, `data-danger` у пункта меню комментариев и т.д. Компоненты рендерят их напрямую (`data-x={cond || undefined}`), скин `corporate` на них опирается.

Автор нового скина не увидит эти атрибуты в типах — только читая CSS скина `corporate` или код компонентов.

## Целевое состояние

Контракт описывает и модификаторы частей, например:

```ts
defineContract({
  name: 'select-input',
  parts: ['option' /* … */],
  partStates: { option: ['highlighted', 'multi'] },
})
```

Компоненты ставят их через типизированный хелпер (как `contractAttrs` для корня), а `themeContracts` показывает полный интерфейс для скина.

## Trade-offs

- **Выигрываем:** скин пишется по типам, а не по чтению чужого CSS; опечатка в имени атрибута ловится компилятором.
- **Риски:** правка ~15 контрактов и компонентов; нельзя менять имена и условия атрибутов, иначе разъедется скин `corporate`.

## Сценарий миграции

- Шаг 1: расширить `defineContract` полями `partStates` / `partAttributes` и добавить хелпер для части.
- Шаг 2: перевести компоненты по одному, сохраняя имена и условия атрибутов; сверять скриншоты и computed styles в состояниях после взаимодействия.
- Шаг 3: проверка в CI: каждый `[data-*]` в CSS скина есть в каком-то контракте.
- Откат: поля в контракте необязательные; компоненты можно возвращать по одному.

## Метрики успеха

- Все data-атрибуты, на которые опирается CSS скина, перечислены в контрактах (проверка в CI).
